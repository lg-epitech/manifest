Ingest API outage on 12 September

A deploy tripled the worker count per pod, the Postgres connection pool ran out, and the API returned 502s for 41 minutes. Nothing was lost: 18,400 requests failed, and all but 1,300 were retried by their clients.

14 September 2026 Laurent Gonzalez Resolved

What happened

At 14:00 UTC on Friday 12 September we deployed ingest-api 2026.09.1. The release was about retry handling. It also carried, in the same PR, a change to WORKERS from 8 to 24 per pod that had been sitting in a branch since August. Nobody flagged it in review because the diff was two characters in a Helm values file and the PR description did not mention it.

Seven minutes later the connection pool on the primary was full. Every new request from ingest-api waited five seconds for a connection, gave up, and returned a 502. The 5xx rate went from a baseline of 0.3% to 63% and stayed there until the rollback finished at 14:48.

The alert took 14 minutes to fire. The 5xx alert averages over a 10-minute window, which is fine for a slow degradation and useless for a cliff. That part bothers me more than the outage itself. We were blind for a quarter of an hour on a Friday afternoon while the graph was vertical.

Why it happened

Each ingest-api worker holds one connection for the life of a request (DB_POOL_MAX=1). With 3 pods and 24 workers each, ingest-api alone can hold 72 connections. Add sync-worker, reporting and admin, and the total lands exactly on the max_connections of 100 that the primary has had since we set it up in 2024. We had never been close to the limit, so nobody treated it as a budget. It is one.

Why the limit is 100

Because 100 is the Postgres default and we never had a reason to change it. Each connection is a backend process with roughly 10 MB of memory, so on this instance 100 is also close to what it can comfortably run. Raising it is not free.

The alert fired late

The 5xx alert has a 10-minute averaging window, so the page went out 14 minutes after the first failed request. This is fixed in the follow-ups below but was true during the incident, and it will be true again for any other alert that uses the same template.

Impact

18,400 requests failed between 14:07 and 14:48, all on POST /transactions and POST /sync. Reads were unaffected because they go to the replica.

Most clients retry with backoff, so 17,100 of those requests were accepted within the hour. The other 1,300 came from the nightly reconciliation job, which does not retry. We replayed them by hand from the dead-letter queue on Monday morning. The idempotency key did its job: no duplicate rows, checked with the query in the appendix.

What we are changing

Decision

Put PgBouncer in transaction mode in front of the primary and cap ingest-api at 8 workers per pod. Agreed with Anna and Tom on 13 September.

  1. Deploy PgBouncer next to the primary in transaction mode with default_pool_size = 20. Laurent, by 19 September.

  2. Set WORKERS back to 8, point ingest-api at the bouncer port, and shorten the 5xx alert window to 2 minutes. Tom, by 19 September.

  3. Add a check to CI that sums workers times pods across services and fails when the total passes 80% of max_connections. Anna, by 26 September.

We are not raising max_connections. It would have bought time on Friday and it would have hidden the actual mistake, which is that nobody knew the budget existed.

Open questions

  • Should sync-worker also go through the bouncer? It holds long transactions, which is the one thing transaction pooling handles badly.
  • The retry-handling change that motivated the release is still not deployed. It needs its own PR, alone this time.
